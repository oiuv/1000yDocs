一、执行结论

这是一个包含 Delphi 7 客户端和主要服务端项目入口、并已通过当前全量构建脚本验证的完整源码仓库，运行基线为未修改的炎黄新章；维护工作限定在 docs/ 和 py1000y/，游戏 Pascal 代码只作事实依据。旧报告存在版本命名、职业等级、端口表达、成熟度判断和风险描述失真，本报告已整体重建，不沿用其宣传式结论。

五、协议、加密与关键数据流

主要封包层

  • 多数 TCP 服务间通信使用 TPacketData 外层。
  • 游戏 UDP 日志使用 TComData，字段为总长、消息号、数据长和 GBK 数据。
  • Gate 到 Balance 的 UDP 状态使用独立 TBalanceData，不能按日志包解析。
  • 客户端/Gate 的加密路径由 uCrypt.pas 和封包代码共同构成，必须按具体调用链描述，不能笼统称作“AES”。

登录顺序

  1. 客户端向 Balance 查询 Gate。
  2. 客户端连接 Gate，进入版本与登录状态机。
  3. Gate 向 Login 校验账号。
  4. 启用付费检查时，Gate 向 Paid 查询独立付费记录。
  5. Gate 通过 DB 获取/保存角色记录，并接入 Game。

Paid 账号记录与 MSSQL/FDB 游戏角色数据独立；当前 Python Paid 不查询角色数据库。

5.1 配置差异必须按组件处理

  • SQL Login 的 [ODBC] 使用 DSN、用户名和密码；是否能使用 Windows 身份验证取决于 DSN/驱动配置，当前项目不新增该整合。
  • SDB Login 与 SQL Login 是二选一登录实现，它们的远程端口和 IP 检查路径不同，不能合并成一个“通用 Login 配置”。
  • Gate 新建 Paid 配置时写入 5999，而读取缺省项时回退 3049；Python Paid 默认 3049。部署必须以服务器实际 GATE.INI 为准。
  • sv1000.ini 控制 Game 到 DB、Battle、Notice 和 UDP 日志目标，不控制 Gate 到 Paid 的地址。

5.2 数据持久化

DB 服务使用自定义 FDB 角色文件结构，启动路径会调用 AddBlankRecord(10000) 预分配空记录。Login SQL 数据库存放账号认证信息；Paid SQLite 存放独立付费模式和到期时间。三类数据职责不同，不应在文档或工具中混称为“玩家数据库”。

六、Game Server 运行模型、数据与脚本

6.1 执行与空间模型

  • Common/uAnsTick.pas 通过多媒体定时器建立 10 ms tick；Game 的管理器在此基础上处理玩家、对象、怪物、技能和脚本更新。
  • 地图 AOI 使用 PHONE_BLOCK_SIZE = 16 的空间块，并向当前块及周围八块广播邻域消息。
  • 玩家、NPC、怪物、门和动态对象由不同类及 Setting 表创建；页面中不能把“拍卖”等未发现消费路径的数据当作已启用系统。

6.2 当前职业与等级

当前炎黄数据确认的生活职业为铸造师、炼丹师、裁缝、工匠、矿工；职业等级为初级工、技能工、熟练工、达人、名人、神工。这些名称来自当前 Init/JobGrade.sdb 和配套资料，替换了原报告中的错误称谓。

7.2 运行约束

  • Paid 无参数只显示帮助，必须显式执行 paid_server.py start，避免误启动多个实例。
  • UDP Logger 的 SDB/CSV 文件保持打开并行缓冲写入；运行中其他编辑器能否读取取决于共享模式。句柄与缓存规模有界，不会随按年运行持续累积全部日志到内存。
  • 运行日志、SQLite 实例、分析结果和备份文件不应新增进版本控制；现有历史数据也不应当作协议规范。

十、维护与部署建议

  1. 冻结证据层：Pascal 源码、炎黄 bin、原始游戏资料和云端神武脚本保持只读；文档引用时标注版本来源。
