# 原版客户端补丁更新

本文说明原版 `cl1000.exe`、`divider.exe` 与 `patch.exe` 的使用和维护，不涉及额外开发的客户端辅助或 Python 实现。

配置名称和程序职责可对照 [readme.chm](readme.chm) 的 **Client（客户端）**、**Patch → Divider.ini**、**Patch → Patch.ini**。直连回退、更新进度、退出后启动游戏及补丁列表重载行为，由维护者根据实际使用的原版程序确认；这些行为未在上述手册章节中完整说明。下述大小限制和传输节奏另经所用更新器的程序实现及实际通信核对。不同发行包应先在独立客户端副本中验证，不把样本结论推广为所有版本的统一行为。

## 程序与配置

| 位置 | 文件 | 用途 |
|---|---|---|
| 客户端目录 | `cl1000.exe` | 补丁更新入口，玩家运行此程序更新客户端 |
| 客户端目录 | `CPatch.ini` | 补丁分配器和备用补丁服务器地址 |
| 客户端目录 | `patch.dat` | 记录客户端已更新到的位置 |
| 客户端目录 | `Client.exe` | 游戏主程序 |
| 分配器目录 | `divider.exe`、`divider.ini` | 向更新器返回 Patch 服务器地址 |
| 补丁服务目录 | `patch.exe`、`Patch.ini` | 提供补丁服务及其配置 |
| 补丁服务目录 | `Filelist.sdb` | 管理补丁条目列表 |

补丁更新与游戏登录是两条独立链路。Divider 的职责类似登录链路中的 Balance，但不能据此认定两者使用相同协议或负载分配算法。`Client.exe` 启动后的服务器选择与登录见[客户端连接与通信](client-communication.md)。

## 连接与更新流程

1. 玩家运行客户端目录中的 `cl1000.exe`，更新器按 `CPatch.ini` 的 `DIV_ADDRESS`、`DIV_PORT` 连接 Divider。
2. Divider 返回 Patch 地址，更新器连接该补丁服务器；若连接 Divider 失败，则尝试配置中的 `PATCH_ADDRESS`、`PATCH_PORT`。
3. 更新器根据本地 `patch.dat` 记录的位置继续处理后续补丁；删除该文件会从头重新处理补丁。
4. 本次更新流程结束后自动启动 `Client.exe`。**结束不等于全部更新成功**：维护者确认，补丁服务器连接超时等情况下也可能进入游戏。

`patch.dat` 用于记录更新进度，不能单凭该文件存在就认定补丁文件完整。本说明不将其解释为单个文件的字节级断点续传，也不规定其二进制格式或异常中断时的精确落盘时机。不要把“游戏已启动”作为补丁发布成功的唯一依据。

## 客户端 `CPatch.ini`

以下统一使用文档示例地址 `203.0.113.10`，部署时须替换。端口 `6059`、`6060` 及后续配置值只是示例，不代表程序默认值。

```ini
[PATCH]
DIV_ADDRESS=203.0.113.10
DIV_PORT=6059
PATCH_ADDRESS=203.0.113.10
PATCH_PORT=6060
```

- `DIV_ADDRESS`、`DIV_PORT`：Divider 的可达地址与监听端口。
- `PATCH_ADDRESS`、`PATCH_PORT`：连接 Divider 失败时尝试的 Patch 地址与端口。

两组地址可以指向同一台主机上的不同服务，也可以分别部署。不要把这里的更新端口与 `addr.txt` 中的游戏 Balance 端口混用。

## 服务端配置

### `divider.ini`

```ini
[DIVIDER]
MESSAGE=The1000Years
CAPTION=1000y Patch Divider
PORT=6059
PATCHSTRING0=203.0.113.10,6060
```

- `MESSAGE`：手册称为客户端更新器提示信息；其它校验作用未核实。
- `CAPTION`：Divider 程序标题。
- `PORT`：Divider 监听端口，对应客户端 `DIV_PORT`。
- `PATCHSTRING0`：向客户端提供的 Patch 地址与端口，格式为 `地址,端口`；地址须能被玩家访问，端口对应目标 Patch 的 `PORT`。

旧手册在 `PATCHSTRING0` 旁注中写了 `DIV_ADDRESS` 与 `PATCH_PORT`，不要将其理解为 Patch 地址必须等于 Divider 地址。按服务职责区分：`DIV_ADDRESS` 指向分配器，`PATCHSTRING0` 指向分配结果；`PATCH_ADDRESS` 则是客户端配置的回退地址。

### `Patch.ini`

```ini
[PATCHSERVER]
PORT=6060
MAXCONNECT=10
VERSION=3
CAPTION=1000yPatch
CLIENTSTRING=The1000Years
```

| 字段 | 说明 |
|---|---|
| `PORT` | Patch 监听端口；本例与 `PATCHSTRING0` 中的端口及客户端回退 `PATCH_PORT` 一致 |
| `MAXCONNECT` | 最大连接数，本例为 10 |
| `VERSION` | 手册称为“版本”；具体校验语义未核实，不将其当作补丁条目数或 Gate 的游戏通信版本 |
| `CAPTION` | Patch 程序标题 |
| `CLIENTSTRING` | 手册称为客户端提示信息；具体校验作用未核实 |

CHM 使用的端口和版本示例与本文不同，不构成流程矛盾。实际配置应保持客户端、Divider 返回地址和目标 Patch 服务之间的对应关系。

## 补丁列表 `Filelist.sdb`

以下保留维护者提供的列表结构，说明文字采用通用示例：

```text
Name,FileName,Date,Process,notice,
1,addr.txt,2023-11-28,Process,更新服务器列表,
2,ect\help.chp,2023-11-28,Process,,
3,ect\help.idx,2023-11-28,Process,,
4,ect\manufacture.atd,2023-11-28,Process,,
5,selectchar.bmp,2023-11-28,Process,更新选角背景,
6,wav\MC000.mp3,2023-12-8,Process,更新音乐,
7,addr.txt,2024-1-4,Process,再次更新服务器列表,
8,snowevent2.bmp,2025-12-24,Process,更新小地图,
```

- `Name`：示例中的补丁编号，按条目递增。
- `FileName`：补丁文件名，示例含 `ect\`、`wav\` 子目录。同一文件可以出现在不同补丁条目中，如两次更新 `addr.txt`。
- `Date`：示例中的日期文本；没有依据表明仅修改日期就能强制客户端重新更新。
- `Process`：示例各行均填写字面值 `Process`；其它取值及执行语义未核实，不自行扩展。
- `notice`：补丁说明，可为空。保留示例的逗号分隔和行末空字段。

列表是补丁索引，不是补丁文件本身；发布时还需提供对应文件，并保持发行包所用的文件目录组织。列表和游戏文本资源保持 GBK 编码与 Windows CRLF 换行，图片、音乐等二进制文件不得转换编码或换行。本文不推断 Patch 程序查找补丁文件的具体根目录。

## 文件大小与传输速度

- **10000 KB 失败属于更新器容量限制**：维护者实测下载进度达到 `10000 KB` 时报错退出。对已核实的原版 `cl1000.exe`，原因是固定接收缓冲区容量不足，继续接收会越界；不是分块序号字段只能表示到 10000。仅更换补丁服务端不能消除此客户端限制。
- **检查压缩封装后的大小**：该样本的静态接收边界为 `10240000` 字节，针对传输用的压缩封装整体，而不是解包后的原始文件。此值不代表恰好达到边界已经实测成功；发布须留出余量，不依赖边界值可用。不可压缩文件还会增加封装开销，不能只凭原文件略小于 10000 KB 就判定可发布。
- **逐块确认影响下载速度**：所用程序每发送一块数据即等待客户端确认，网络往返与两端处理节奏都会影响吞吐。已测环境约为 `27 KiB/s` 的传输节奏，可以解释维护者约 8 M 文件耗时 5 分钟的体验，但不是已确认的固定带宽上限。

`MAXCONNECT` 是连接数限制，不是带宽或下载速度配置；现有手册未说明可调整的速率参数。排查速度时区分原始文件大小、实际传输大小、网络条件和处理耗时，不仅凭体感判断限速。

发布接近边界的文件前，应在独立测试环境验证完整传输，并比对目标文件与补丁源文件。超限文件不要交给该更新器发布，应采用经过验证的其它分发方式；不要反复重置进度进行越界下载测试。上述限制仅适用于已核实样本，不能直接认定其它发行版本具有相同边界。

## 发布与排查

**每次修改 `Filelist.sdb` 后必须重启 `patch.exe`。只保存列表不会让运行中的服务使用新列表，客户端仍会更新旧补丁。**

建议按以下步骤维护：

1. 备份原列表及被替换的补丁文件，准备新增文件；为保留既有客户端更新进度，优先追加补丁条目，不随意重排或重编号已有记录。
2. 核对文件名、子目录、列表字段和端口配置，然后在维护窗口重启 `patch.exe`。
3. 用独立测试客户端保留 `patch.dat` 验证增量更新；需要验证从头更新时，先备份该测试副本的 `patch.dat`，再删除它重试。不要未经备份重置玩家的更新进度。
4. 检查实际目标文件内容；有可执行文件更新时同时核对其版本。不能只看 `Client.exe` 是否启动。

| 现象 | 检查重点 |
|---|---|
| Divider 不通仍能更新 | 检查客户端配置的 Patch 回退地址是否可达 |
| 保存列表后仍是旧补丁 | 确认修改的是运行实例使用的列表，并已重启该 `patch.exe` |
| 每次都从头更新 | 检查 `patch.dat` 是否被删除、清理或未保留；不要直接修改其二进制内容 |
| 游戏能启动但文件未更新 | 检查补丁连接是否超时、目标服务与列表是否正确，并核对实际文件 |
| 下载进度到 10000 KB 报错退出 | 检查封装后传输大小是否超出更新器接收容量；不要反复重置 `patch.dat` 重试超限文件 |
